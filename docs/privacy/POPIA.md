# POPIA engineering controls and owner decisions

Reviewed 8 October 2026. This is an implementation map, not a legal-compliance certification. The municipality is the proposed responsible party; its registered Information Officer must approve the lawful basis, resident notice, operator agreements, retention schedule and identity-verification procedure before processing real resident data. The demo uses synthetic data only.

The eight conditions below follow Chapter 3 of the [Protection of Personal Information Act 4 of 2013](https://www.justice.gov.za/legislation/acts/2013-004.pdf), supported by the [Information Regulator's conditions index](https://inforegulator.org.za/knowledge-base/category/popia/chapter-3-conditions-for-lawful-processing/). Sections 11–14, 18–25 and 72 require decisions that software alone cannot establish. Public-service duties may support a lawful basis other than consent; the owner must determine that basis and any statutory record obligations rather than treating a checkbox as universal permission.

A contact setting is not registration. |
| 2. Processing limitation (§§9–12) | Explicit current-purpose consent required for production web, Open311 and voice-tool intake; contact and callback consent are separate. Contacts are optional. ## Consent and minimisation

`PrivacyConsent.Version` is `civicops-popia-v1`. `PrivacyConsent.Text` is the authoritative full text, and `Purpose` limits processing to assessing, routing and managing the municipal service issue, with separately requested service updates. Production JSON requests use `privacyConsentAccepted:true` and `privacyConsentVersion:"civicops-popia-v1"`; Open311 uses `privacy_consent_accepted` / `privacy_consent_version`; agent tools use those snake-case fields. The intake form starts unchecked. Voice provisioning instructs the agent to explain purpose, ask explicitly and avoid inferred consent. An unlinked live post-call transcript without current consent creates an alert receipt, not a case.

Each new case records the receipt. Continuing a call, supplying a phone number or caller ID never constitutes contact consent. Demo/internal legacy intake with no explicit fields records `legacy-or-synthetic-unverified` and `Accepted=false`; old records are never retroactively claimed to have consent. The municipality must review legacy imports before any real pilot.

Optional email/phone live separately from narrative snapshots: tenant-specific `resident-contacts.json` in file mode, or tenant-bound durable documents in PostgreSQL mode. Case state contains a contact digest, and restart validates it against the audit-authenticated state. Legacy contacts migrate through an appended audit event without rewriting historic hashes. Standard resident/staff views omit contact values; only the verified administrator access export returns them. Contacts are hydrated internally for consented service delivery.

In file mode, contact and case files are individually atomically replaced. A crash between writes can produce a digest mismatch and disable reads/writes on restart; restore a verified backup rather than editing the digest. This fail-closed behavior is tested, including repeated read attempts. PostgreSQL mode implements one transaction for case, contact, audit and outbox writes, with fresh reads and optimistic concurrency across application instances. See [storage boundaries](../operations/STORAGE.md) and [tested local backup/restore](../operations/BACKUP_RESTORE.md). Production volume/database encryption, backup key custody and deployment recovery objectives remain owner-pending.

## Redaction policy

`PiiRedactor` replaces email addresses, South African-style phone numbers, international numbers with `+` or `00` prefixes and 7–15 significant digits, thirteen-digit possible SA IDs and names following explicit labels such as `My name is`, `Resident name:` and `Contact name:`. JSON string values in explicit name fields (`name`, `fullName`, `residentName`, `contactName`, `callerName`, `displayName`), contact fields (`phone`, `phoneNumber`, `contactPhone`, `mobile`, `email`, `contactEmail`) and identity fields (`identityNumber`, `saId`) are removed regardless of formatting, including snake-case aliases. It preserves JSON shape, numeric values, service meaning, machine identifiers (`id`, `workerId`) and case references. A thirteen-digit pattern is conservatively removed without claiming it is a validated identity number. Ordinary unlabeled names, addresses, local numbers outside the recognised phone pattern and unusual formatting cannot reliably be detected by this rule policy.

The policy applies to all backend LLM request string values, stored model output, new audit detail text, application log formatters/exception output, intake narratives and received voice summaries/transcripts. No raw PII logging or whole-provider-body logging is permitted. Explicit optional contact fields remain available only to consented service delivery and verified administrator access exports.

**Provider boundary:** browser/telephone ElevenLabs speech and hosted-widget messages reach ElevenLabs before CivicOps receives them. CivicOps cannot apply its backend redactor before that provider's speech/hosted-LLM processing. Provider account privacy controls, retention, upstream redaction, processor contracts and any cross-border transfer assessment remain owner-pending. No live voice/model processing was exercised. The application does not claim its backend rule policy anonymises every name or all provider-held data.

## Retention and local deletion

- `CIVICOPS_RETENTION_DAYS`: existing closed-case snapshot purge, 1–36500 days after the closing milestone; now removes its separate contacts, scrubs delivered integration contact payloads and removes matching local email outbox files. Case-reference/idempotency audit tombstones remain.
- `CIVICOPS_PII_RETENTION_DAYS`: optional independent closed-case contact retention, same range and milestone; retains the service case while clearing email/phone/contact permission with an audited tombstone.
- Pending/dead-letter integration cases remain protected from scheduled retention. An administrator may explicitly anonymise a verified request; queued delivery payloads are erased and further delivery/retry is suppressed.
- The hourly service handles every tenant. The authenticated admin `/api/retention/purge` exposes manual execution. Invalid/blank settings disable the applicable schedule; the owner must publish approved periods before a real pilot.

Local anonymisation removes contact, narrative, area, transcript/metadata, conversation ID, model evidence and drafts from the current case, removes local email outbox files and erases local integration request payloads. A case reference, workflow metadata, the consent receipt, DSR record and an audit tombstone remain. Prior immutable audit may contain historic personal detail; its hashes are preserved. Provider records, backups, exported JSON copies and older audit require a separate Officer-led retention/erasure process. Filesystem deletion is not a secure wipe of storage media.

## Administrator data-subject workflow

The Administration → Privacy requests panel implements the same tenant-scoped, CSRF-protected API:

1. POST `/api/admin/privacy/requests` with `{referenceNumber, action:"access"|"correction"|"anonymisation", requestNote}`. The note is bounded and redacted; use a case reference, not an identity document.
2. Verify identity through the municipality's approved external procedure. POST `/{id}/verify` with `{verificationNote}` describing method/outcome without names, ID numbers, document copies or tokens. The server records the administrator and time; it does not independently verify identity.
3. POST `/{id}/fulfil`. Access returns a no-store JSON attachment of the local case, optional contact and consent receipt. Correction/anonymisation require `expectedVersion`; correction accepts optional `description`, `contactEmail`, `contactPhone` and separately asserted `consentToContact`. Anonymisation suppresses outstanding local integration delivery. Each fulfilment extends the audit chain; request state is digest-bound to its latest system audit record.

GET `/api/admin/privacy/requests` returns only the signed-in municipality's records. Service-account tokens cannot receive the admin policy. Export recipients, response deadlines, lawful exemptions, authenticity of external verification and completion of provider/backup deletion remain staff obligations. Re-run local verification after changing the policy; evidence is in [`PrivacyTests.cs`](../../tests/CivicOps.Tests/PrivacyTests.cs) and [`docs/security/ASVS_L2.md`](../security/ASVS_L2.md).
