# Security policy

CivicOps has locally tested application security and privacy controls. Production municipal identity, hosting, provider contracts and operational response remain owner validation. Use synthetic data until the municipality has accepted the [threat model](docs/security/THREAT_MODEL.md), [ASVS gap review](docs/security/ASVS_L2.md), [POPIA mapping](docs/privacy/POPIA.md) and [DPIA](docs/privacy/DPIA_TEMPLATE.md). This engineering work is not an independent security certification or a declaration of legal compliance.

## Report a vulnerability privately

Use the repository's **Security → Report a vulnerability** channel when private reporting is enabled. If it is unavailable, use an existing private channel to the repository owner and ask for a secure reporting destination before sending details. The owner must enable private reporting and publish a maintained security contact before public deployment; no unverified mailbox or response service is advertised here. The configured Information Officer contact handles privacy/data-subject requests and is not automatically a vulnerability-reporting mailbox.

Provide the affected commit/version, component, impact, minimal synthetic reproduction and the relevant request/response or logs with credentials and personal data removed. Do not publish resident records, transcripts, secrets or exploit details in public issues. Do not test a live municipality or provider without its explicit authorization. Test only your isolated instance with synthetic identities/data; avoid denial of service, account creation, access to another person's records or external provider writes. If sensitive data is encountered, stop access, retain only the minimum redacted evidence and report privately.

Maintainers aim to acknowledge reports within three working days, give an initial assessment within ten working days and agree an update cadence with the reporter. These are policy targets, not a tested or staffed service-level guarantee. Critical confirmed issues should be contained immediately where feasible; supported fixes and coordinated disclosure dates depend on impact and deployment access. Agree public disclosure after a fix and reasonable deployment time; no bounty, legal safe-harbor agreement or institutional response contract is implied. Credit is optional and only with the reporter's consent.

## Supported scope and incident handling

The latest local CivicOps application is the maintained engineering version. Previous snapshots, personal forks and unreviewed live deployments do not receive a promised backport. Remote publication/branch protection, staffed reporting, municipal operational ownership and a production release policy remain owner-pending.

For a confirmed incident, the deployment owner contains affected access, rotates/revokes exposed credentials, preserves protected audit evidence, assesses scope with the Information Officer and processor contacts, and applies the municipality's approved notification and recovery procedures. Technical operators must not decide legal notification duties from this repository alone. Record investigation and remediation using redacted metadata, restore from validated backups and reassess the threat model before reopening service.

## Enforced application boundaries

- Staff use OpenID Connect authorization code + PKCE, explicit role/municipality mappings and opaque server-side session tickets. Production cookies are Secure, HttpOnly, SameSite=Lax and host-only. Cookie-authenticated state changes and sign-in transitions require framework antiforgery tokens in `X-CivicOps-CSRF`. Scoped service-account/training bearers and signed provider webhooks use non-cookie authentication and are CSRF-exempt by design. See [HTTP security](docs/security/HTTP_SECURITY.md) and [RBAC](docs/RBAC.md).
- The complete method/route permission matrix is enforced on the server. Municipality and crew assignment guards constrain object access. Auditors cannot mutate operational work; high-hazard approval/assignment and overrides require supervisor/admin authority. Case references, caller labels and conversation identifiers never grant general staff authorization.
- Administrator-issued users and service accounts retain credential hashes, show random tokens once, and support expiry/rotation/revocation. Legacy environment dispatcher/tool/training credentials remain documented default-tenant bootstrap mechanisms; use SSO/scoped accounts for routine production access. Explicit demo mode retains visibly unverified synthetic identities and public demonstration credentials.
- Strict per-response nonce CSP forbids `unsafe-inline` and inline event handlers; provider script/network origins are included only for configured voice. SDK/widget bundles are version-pinned with SRI. Response controls include nosniff, private referrer policy, frame-ancestors/DENY, COOP/CORP, disabled camera/geolocation and microphone self permission only for configured voice. HSTS applies to production HTTPS; every subdomain must support HTTPS before deployment. Live widget/microphone/CDN behavior still needs owner validation.
- Bounded request bodies, JSON depth, DTO fields, allowlisted roles/catalogue/tool identifiers and control-character/Unicode/header validation limit untrusted input. Chunked requests follow the same limits. Malformed or unexpected requests return controlled errors/ProblemDetails; production exceptions omit stack traces/provider bodies. Tenant/principal/IP quotas separate intake, authentication, staff, tools and training; caller forwarding headers do not supply identity.
- ElevenLabs/Zendesk webhooks verify HMAC over exact raw bytes plus timestamp using constant-time comparison, freshness windows and durable replay markers. Tool mutations bind to the original conversation. Providers do not grant agents approval/assignment/admin authority. Agents recommend and draft; structured output is bounded and validated, danger rules independently floor urgency, and uncertain reasoning falls back explicitly.
- Public status omits resident narrative/contact/transcripts/internal decisions. Contact details are optional and stored separately from narrative snapshots; versioned purpose/consent is recorded. PII redaction protects log and LLM boundaries. Administrative access/export, correction and local anonymisation require recorded identity-verification notes and an audit trail. Pattern/name recognition cannot guarantee that every indirect identifier is detected.
- `CIVICOPS_RETENTION_DAYS` controls old closed-case snapshots; `CIVICOPS_PII_RETENTION_DAYS` separately controls old closed-case contact fields. Undelivered/dead-letter cases are protected; purge records redacted audit tombstones and retained submission receipts prevent accidental recreation. Immutable historical audit, external providers, backups and workforce records need their own approved retention/erasure policy; local anonymisation is not complete erasure.
- Environment and mounted-file (`*_FILE`) secret sources are fully implemented through a shared abstraction. Explicit mounted files take precedence and fail closed on invalid content. Readiness reports names/states, never secret values; generic failures and sentinel regression tests cover logs/exceptions. Azure Key Vault/HashiCorp Vault are documented adapter seams, not live SDK integrations. See [secret management](docs/security/SECRETS.md).
- Audit mutations link previous hashes and retained case state; detected mismatches block further writes. File contents flush before atomic replacement, a data-directory lease prevents two processes sharing stores, and durable delivery/certification intents support recovery. Model/provider failures produce generic codes; demo always forces simulated provider delivery and email outbox. Missing dependencies degrade to honest disabled/simulated modes.

## Deployment responsibilities and residual risk

Use one application process per private data directory. The JSON/contact/request stores use process-local gates and multiple files, not a distributed transactional database; interrupted cross-file updates can fail closed and require protected operator recovery. Directory fsync, external audit anchoring, application-level at-rest encryption, distributed sessions/storage and global issuer session management remain absent. Sessions expire on process restart; external SSO roles refresh at sign-in/expiry. A filesystem administrator can read plaintext and rewrite an entire unanchored chain, even though routine application tampering is detected.

The owner must supply verified HTTPS/ingress and proxy trust, issuer MFA/access policy, least-privilege host accounts, private volume/mounted-secret permissions, encryption and key custody, protected backups/restore exercises, storage quotas, monitoring/remote alerts and incident response. Do not share the application host with untrusted services. Container/deployment assets are statically reviewed only on this box: Docker execution has not occurred. Live provider credentials/permissions, cross-border processing, emergency escalation, language/voice quality and actual AMD model/hardware behavior require separate validation.

A public reference gives minimal case status, not verified resident identity. Private voice-session issuance is rate limited but is not a municipal identity-proofing service. A checkbox/voice assertion is not independently authenticated consent. DSR identity verification is a privileged administrator assertion; the municipality must define acceptable verification without collecting unnecessary ID copies. Legacy/shared bootstrap identities weaken individual attribution; disable demo and replace bootstrap access for pilot operations. Per-process quotas do not defeat distributed abuse; network capacity and operational alerts are deployment controls.

CivicOps is not an emergency service. Synthetic prompts direct emergencies to applicable emergency channels; no crew arrival, resolution time or verified geographic location is promised. Formal municipal safety/accreditation and resident-data review are required before a pilot. Prompt injection can produce plausible but wrong recommendations even with schemas and redaction; retain human review and test the configured model.

## Development security checks

Run the repository verifier, then the explicit supply-chain inventory gates:

```bash
./scripts/verify.sh
./scripts/security_dependencies.sh
./scripts/sbom.sh "$TMPDIR/sbom.cdx.json"
```

Release enables `.NET` latest-recommended analyzers and warnings as errors. Tests preserve regression counts; browser smoke asserts zero CSP violations. CI also declares C#/JavaScript CodeQL, dependency review, direct/transitive NuGet advisory checks, npm audit for any tracked manifest, pinned CycloneDX generation and SBOM artifacts. An npm manifest without a lockfile fails the gate. Only independent test-fixture allocation-performance suggestions are suppressed; security analyzers remain enabled. [CI/SBOM scope and local results](docs/security/CI_SECURITY.md).

Run `gitleaks detect --source . --log-opts="--all" --redact` and `gitleaks dir . --redact` before handoff. Blank `.env.example` placeholders are the only committed environment inventory. Fake credentials have explicit test names and narrowly scoped scanner exceptions. These checks cover the working tree and locally present refs, not unfetched cached pull-request refs. Do not commit personal data; report suspected exposure through the private channel above.
